## The GitHub Action

The action lives in
[stokaro/unswell-action](https://github.com/stokaro/unswell-action). Pin the action
commit and the CLI version independently:

```yaml
name: Editorial
on: [push, pull_request]

permissions:
  contents: read

jobs:
  unswell:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5
      - uses: stokaro/unswell-action@03845fae652abdbd9588031a374d1a54155aa24c
        id: unswell
        with:
          version: 0.1.0-alpha.25
          config: .unswell.yaml
          paths: |
            README.md
            docs
            src
```

The CLI release has to exist before the action runs. Once it does, the action
verifies the downloaded archive's SHA-256, passes each input as a process
argument, and keeps the pass, failure and error outcomes apart (it doesn't
collapse them into one). The JSON and SARIF file paths come back as step outputs,
and after installation the analysis is offline.

Unit tests against local archives can't stand in for a check of the public
download. So the action repository has a `Verify published release` workflow: it
proves that bad prose and malformed source fail their steps with the expected
codes and report contents.

## Any other runner

Install the CLI and run it. The pattern that keeps a pipeline honest is one
analysis writing the artifact the pipeline keeps:

```sh
unswell check README.md docs/ src/ \
  --config .unswell.yaml \
  --report text:- \
  --report sarif:artifacts/unswell.sarif
```

Exit code 1 is a policy failure and should fail the job. Exit code 2 is an
operational error; treat it as a pass, and a broken parse becomes a green build.
For a reporting job there's `--no-gate`, which collects findings without failing
on style (it still fails on an operational error).

For a repository with existing debt, `--baseline .unswell-baseline.json
--gate-mode new` accepts what was reviewed and gates what is new. Because the
baseline path belongs to the invoking workflow, a pull request has no way to
point the run at a different debt file through YAML.

<Note>
  A source pull request must not control its own policy: pin the release, pin the
  profile version, and compare the configuration hash from `unswell config
  explain` against the value you reviewed.
</Note>

## Publishing SARIF

The SARIF report is validated against the published 2.1.0 schema and was imported
by Sarif.Multitool, the reference implementation, with no validation results at
any level. That's one report accepted by one consumer. Other consumers apply
their own rules: GitHub code scanning, in particular, enforces limits of its own,
and only an upload to it tests those.

## The MCP server

`unswell-mcp` is a separate executable and a separate Go module, so the MCP SDK
stays out of the core module. What the two executables share is the engine:
extraction, policy, rules, scores, gate and source coordinates.

```sh
make build-mcp
bin/unswell-mcp --config /absolute/path/to/project/.unswell.yaml
```

Configure a stdio client to launch the absolute executable path with `--config`
and the policy path as separate arguments. The executable reserves stdout for
protocol frames; startup errors, help and `--version` go to stderr. Without
`--config` the server uses builtin defaults (it doesn't search for a file), and
`--timeout 30s` bounds each check, to a maximum of five minutes.

Four tools. The first two run the fixed policy:

`unswell_describe` takes an empty object, or a logical file such as
`{"file":"docs/reference/api.md"}` to resolve the file overrides that would apply
(it opens no source file). What comes back is the supported formats and contexts,
the rule catalog, the effective policy with its hash, and the build version.

`unswell_check` takes source contents directly, between 1 and 256 of them. Each
`name` labels evidence and takes part in exception matching; the server never
opens it as a file. If you omit `format`, the grammar is inferred from the name
or a shebang.

```json
{
  "sources": [
    {
      "name": "src/Client.cs",
      "format": "csharp",
      "text": "class Client { string message = \"The connection closed.\"; }"
    }
  ]
}
```

The response carries an `outcome` beside the engine result: `pass`,
`policy_failure`, or `error` with `isError` set. Malformed tool arguments return a
tool error before analysis and may carry no engine result at all. And a transport
cancellation leaves the draft unchecked, so check it again.

<Note>
  Tool arguments cannot disable the gate, change a rule or supply configuration.
  An assistant that fails a check should revise the draft and check again.
</Note>

The other two tools let the calling assistant review a draft in context.
`unswell_review_request` returns the editorial rubric and the document's items:
sentences, paragraphs without separate sentences, and longer fragments. Which
items need revision is the assistant's call, and it sends its flags to
`unswell_review_submit`. There the server binds each quote to an exact byte range
and rejects a flag whose quote does not occur inside one segment of its item.
Since these findings are the assistant's own judgments, they stay advisory: the
gate ignores them.

Repeat `--feature ID` at startup to collect block measurements, and
`--feature activation/<rule id>` to collect one rule's activation. The rule has to
exist in the startup catalog, and selecting it does not enable it. The selection
is fixed while the server runs (clients can't change it). The measurements are
for reading only: the gate and every probability stay the same with or without
them.

`--baseline` with `--gate-mode new` loads reviewed debt once at startup. Tools can
inspect the selection and check drafts under it; they cannot create or update it.
Restart after a reviewed update.

## Checking Unswell with Unswell

`make dogfood` runs the built CLI over this repository under its own strict
policy, then feeds a deliberate violation through five contexts (each one has to
exit 1).

`make dogfood-mcp` does the same work through bounded MCP subprocesses and compares
their combined results with the complete CLI scan. Everything has to match: policy
hashes, build revisions, findings, exclusions, gate outcomes and the measurements
that were asked for.
